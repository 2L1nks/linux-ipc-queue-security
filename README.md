# Исследование безопасности очередей сообщений ядра Linux

**Курсовой проект** · целевая ОС: **Kali Linux 2026.2** · языки: C, Bash, Python 3.


## 1. Цель и задачи

**Цель:** исследовать System V IPC message queues и POSIX message queues в Linux с точки зрения безопасности, изучить возможные классы ошибок и провести воспроизводимые проверки разграничения доступа, лимитов и изоляции.

Задачи: теория IPC; модель безопасности; обзор CVE; эксперименты; рекомендации; выводы. Оформление итогового академического отчёта проводится после получения фактических результатов со стенда.

## 3. Стенд и безопасность

1. Создать отдельную ВМ Kali Linux 2026.2 в VirtualBox, VMware или KVM с достаточными для обычной Kali ресурсами (ориентир: 2 vCPU и 4 ГиБ RAM). Зафиксировать версию системы и ядра командами ниже. Наличие конкретного ядра заранее **не предполагается**.
2. Пока есть сеть, установить инструменты и при необходимости авторизоваться в GitHub. Затем отключить сетевой адаптер ВМ **перед опытами**, сделать снимок состояния `ipc-before-tests`.
3. Опыты ограничены на уровне программ: не более 16 очередей по 4096 байт для наблюдения за ресурсами, не более 32 очередей для проверки количества, ожидание не более 15 секунд. Сильный DoS и перезагрузка ядра **не выполняются**.
4. **Не запускать** все программы через `sudo`: базовые тесты должны работать с минимальными правами. `sudo` нужен только для проверки DAC от другого пользователя и IPC namespaces.
5. Не устанавливать глобально `sysctl -w kernel.msg...` в основной системе; для этого предусмотрен отдельный IPC namespace. Если `unshare` не работает — записать отказ как ограничение стенда, а не обходить его.

### Этап C: сведения о Kali и ядре

```bash

```

Смотрите реальные значения вашей системы; значения на разных ядрах и в разных namespaces могут различаться. **[СКРИНШОТ 03]** версия Kali, `uname -r`, лимиты IPC.

### Этап D: сборка и базовые тесты

```bash
make
make test
./bin/sysv_demo
./bin/posix_demo
```

`make` компилирует все исходники в `bin/`. `make test` проверяет две реализации IPC и ошибки превышения лимитов. В базовых демонстрациях родитель создаёт очередь, дочерний процесс получает сообщение, после чего ресурс удаляется. **[СКРИНШОТ 04]** успешная компиляция. **[СКРИНШОТ 05]** успешный обмен System V/POSIX.

### Этап E: наблюдение за системными вызовами

```bash
strace -f -e trace=msgget,msgsnd,msgrcv,msgctl ./bin/sysv_demo
strace -f -e trace=mq_open,mq_timedsend,mq_timedreceive,mq_unlink,mq_getsetattr ./bin/posix_demo
ipcs -q
ls -la /dev/mqueue
```

`strace -f` показывает системные вызовы также у дочернего процесса; список событий после `-e trace=` ограничивает лишний вывод. `ipcs -q` показывает System V очереди, а `/dev/mqueue` — точку представления POSIX-очередей, если файловая система смонтирована. После корректной очистки учебные очереди не должны оставаться. **[СКРИНШОТ 06]** системные вызовы System V. **[СКРИНШОТ 07]** POSIX.

### Этап F: лимиты и ошибки

```bash
./bin/sysv_limits 4096
./bin/sysv_limits 2048
./bin/posix_limits 4
./bin/posix_limits 2
./bin/queue_count_probe 6
```

Для System V устанавливается `msg_qbytes` **только созданной программой очереди** через `IPC_SET`, не системный `sysctl`. Для POSIX `mq_maxmsg` задаётся при создании. `EAGAIN` (`errno=11`) означает, что неблокирующая отправка в заполненную очередь невозможна; `EINVAL`/`EMSGSIZE` означает некорректный размер. `queue_count_probe 6` только показывает создание 6 очередей и **не должен** выдавать `ENOSPC` при обычном высоком `MSGMNI`. **[СКРИНШОТ 08]** оба размера System V. **[СКРИНШОТ 09]** оба режима POSIX.

### Этап G: полный автоматический прогон (без root)

```bash
./scripts/run_experiments.sh
ls -lt results/runs
find results/runs -name 'limit_comparison.svg'
```

Скрипт собирает `environment.txt`, демо-логи, ошибки ограничений, трассировку (`strace`, если установлен), состояния IPC/памяти **до / во время / после** ограниченной нагрузки, и график `limit_comparison.svg`. Каталог имеет вид `results/runs/ГГГГММДДTHHMMSSZ`. Показатель `Slab` шумный и зависит от других процессов; сравнение — иллюстрация наблюдения, а не доказательство причинной утечки памяти.

**[СКРИНШОТ 10]** результат скрипта с путём к логам; **[СКРИНШОТ 11]** `resource_state.log`; **[СКРИНШОТ 12]** открытый SVG-график.

### Этап H: права DAC (нужно sudo)

```bash
./scripts/permissions_test.sh
```

Скрипт создаёт временную очередь с правами `0600`, копирует маленькую проверочную программу во временную директорию `/tmp` (чтобы `nobody` мог её запустить, даже если ваш домашний каталог закрыт) и запускает попытку чтения от `nobody`. Ожидаемо `EACCES` / `DENIED`, после чего удаляет очередь и временную копию. Это не демонстрация обхода прав. **[СКРИНШОТ 13]** `DENIED ... EXPECTED`.

### Этап I: IPC namespaces и sysctl (нужно sudo, исключительно ВМ)

```bash
sudo ./scripts/namespace_test.sh
sudo ./scripts/sysctl_namespace_test.sh
```

Первый скрипт создаёт очередь с известным ключом в исходном IPC namespace и проверяет, что новый IPC namespace не видит её (`ENOENT`). Второй в **новом IPC namespace** задаёт `kernel.msgmnb=2048`, `kernel.msgmni=4`, после чего проверяет поведение ограничений и отсутствие изменения настроек в исходном namespace. Все создаваемые очереди очищаются.

**Возможная штатная ошибка:** `unshare: unshare failed: Operation not permitted` при отсутствии `CAP_SYS_ADMIN`, в контейнере или из-за ограничений стенда. Зафиксируйте её; нельзя объявлять тест пройденным. Не отключайте механизмы защиты системы ради выполнения.

**[СКРИНШОТ 14]** различие inode IPC namespaces/`HIDDEN` или отказ. **[СКРИНШОТ 15]** сравнение лимитов внутри и снаружи namespace / ожидаемый `ENOSPC`.

### Этап J: проверка отсутствия оставшихся ресурсов

```bash
ipcs -q
ls -la /dev/mqueue
make test
```

Если в `ipcs -q` осталась **только ваша** тестовая очередь, удалите её через `ipcrm -q ID`, где `ID` взят из строки именно вашей очереди. Не удаляйте очереди неизвестных процессов и не выполняйте массовую очистку `ipcrm -a`. **[СКРИНШОТ 16]** отсутствие оставшихся тестовых объектов (фоновые IPC-объекты других программ могут присутствовать).

git init -b main
git add .

Включите сеть ВМ **после опытов**, пройдите авторизацию GitHub CLI и создайте приватный репозиторий:

```bash
gh auth login
gh auth status
gh repo create linux-ipc-queue-security --private --source=. --remote=origin --push
git remote -v
git status
```

Команда `gh repo create` создаёт новый репозиторий **в вашей учётной записи**. Если он уже существует, **не запускайте** её повторно: добавьте `origin` вручную и выполните `git push -u origin main` (см. `docs/06_report_plan.md`). Локальная сборка и проверка в любом случае проводятся в вашей Kali.

### Как добавлять результаты

1. Возьмите путь `OUTPUT_DIR` последнего запуска из терминала.
2. Просмотрите текстовые логи и график: скомплектуйте только необходимые доказательства, удалите системные идентификаторы. В `results/sanitized/` переместите отобранные файлы, скриншоты положите в `screenshots/`.

**Важно:** исходные сырые данные `results/runs/` сохраните локально до оформления отчёта. Не принуждайте Git отслеживать их все через `git add -f`.

## 5. Что означает результат

- `SYSV RECEIVED`, `POSIX RECEIVED`: IPC функционирует в текущем ядре.
- `errno_full=11` (`EAGAIN`): ожидаемая безопасная реакция на достижение лимита, **не CVE**.
- `SYSV_OVERSIZE ... errno=22`: превышение допустимой длины сообщения System V (`EINVAL`).
- `POSIX_OVERSIZE ... errno=90`: сообщение превышает `mq_msgsize` (`EMSGSIZE`). Значения errno характерны для Linux на данной архитектуре; в тексте отчёта предпочтительнее указывать символическое имя.
- `PERMISSION DENIED`: проверено разграничение доступа для второго пользователя.
- `NAMESPACE HIDDEN`: очередь из исходного пространства IPC недоступна в дочернем.
- `QUEUE_COUNT ... stop_errno=28`: `ENOSPC` после снижения `MSGMNI` **в отдельном IPC namespace**.

В документах **не утверждается**, что используемое ядро Kali уязвимо к рассмотренным CVE: для такого заключения нужны точная версия, патчи дистрибутива и анализ upstream/downstream исправлений, а не только `uname -r`.
