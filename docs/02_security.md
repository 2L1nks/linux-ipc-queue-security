# Глава 2. Модель безопасности очередей сообщений

## 2.1. Механизмы защиты

| Механизм | Что защищает | Ограничение / риск |
| --- | --- | --- |
| `ipc_perm`, права `0600` / `0640` | Доступ к объекту System V с учётом UID/GID | Слишком широкие права, ошибки владельца, исключения для capabilities |
| POSIX-режим доступа в `mq_open` | Право на открытие именованной POSIX-очереди | Небезопасное имя, `umask`, оставленный после работы объект |
| `CAP_IPC_OWNER` | Влияние на проверки прав System V IPC | Процессы с capability могут обходить обычные DAC-проверки |
| `CAP_SYS_RESOURCE` | Некоторые привилегированные операции/лимиты | Расширяет возможности процесса; не раздавать без необходимости |
| IPC namespaces | Изоляция пространства System V и POSIX очередей | Не заменяет защиту процессов, памяти и других namespaces |
| `kernel.msgmax` | Размер одного System V сообщения | Не ограничивает автоматически совокупную активность всех очередей |
| `kernel.msgmnb` и `msg_qbytes` | Объём данных в одной System V очереди | Рост числа очередей сохраняет риск ресурсного давления |
| `kernel.msgmni` | Число System V очередей в IPC namespace | Лимит сам по себе не исключает небезопасную реализацию приложения |
| `fs.mqueue.*` и `mq_attr` | Лимиты POSIX очередей | Нужно учитывать допустимые значения и `RLIMIT_MSGQUEUE` |
| `RLIMIT_MSGQUEUE` | Ограничение ресурсов POSIX очередей для реального UID (по правилам ядра) | Может отличаться для root и других UID; приложение должно обрабатывать отказ |
| Актуальные обновления ядра | Исправления известных классов ошибок | `uname -r` недостаточен для проверки downstream/backport патчей |

`CAP_IPC_LOCK` относится к блокировке памяти и **не является основной capability для доступа к очереди**; нельзя смешивать её роль с `CAP_IPC_OWNER`. Детали см. в `capabilities(7)`.

## 2.2. Граница доверия

Пользовательское приложение контролирует входные параметры (`mtype`, размеры и тела сообщений, имена POSIX объектов). Ядро должно валидировать запрос, проверить права и разрешённые размеры, корректно сериализовать конкурентные операции и безопасно освободить объект. Ошибки в любой из этих областей могут привести к разным последствиям.

## 2.3. Карта риска

| Риск | Причина | Что делаем в курсовой |
| --- | --- | --- |
| Исчерпание доступного объёма очереди | Частые отправки без получения | Достижение `EAGAIN` с лимитом 2–4 КиБ |
| Превышение одного сообщения | Некорректный `msgsz` / `mq_msgsize` | `EINVAL` для SysV, `EMSGSIZE` для POSIX |
| Чрезмерное число объектов | Нет ограничений/очистки | `queue_count_probe` до 32, опционально `MSGMNI=4` в namespace |
| Доступ другого UID | Слишком широкие права / ошибки | Тест с `nobody`, ожидаемый `EACCES` |
| Обмен между изолированными процессами | Ошибка пространства имён | `unshare --ipc`, ожидаемый `ENOENT` |
| Race condition, UAF | Ошибка жизненного цикла объектов ядра | Обзор CVE; **эксплуатация не проводится** |
| Heap manipulation через `msg_msg` | Изменяемый размер/содержимое объекта в некоторых версиях | Только аналитическое объяснение; **не доказательство дефекта очередей само по себе** |

## 2.4. Принцип минимальных привилегий

По возможности создавать объект с `0600`, не работать от root, использовать `O_CREAT | O_EXCL` у POSIX для обнаружения неожиданных коллизий, корректно завершать работу (`IPC_RMID`, `mq_unlink`). Повышение лимитов, полномочия `CAP_SYS_ADMIN` и изменение глобальных `sysctl` не должны требоваться прикладному коду.

## 2.5. Вывод

Изоляция, дискреционное управление доступом и ограничения ресурсов обеспечивают несколько уровней защиты, но не исключают ошибок конкурентной работы и освобождения объектов в ядре. Эксперименты подтверждают проверяемые свойства конкретной Kali, а не наличие уязвимости CVE.
