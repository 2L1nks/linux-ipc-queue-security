# Глава 4. Эксперименты: протокол для Kali Linux 2026.2

## 4.1. Подготовка и условия воспроизводимости

Стенд — собственная ВМ Kali Linux 2026.2; в отчёте добавить гипервизор/его версию, число CPU, память, `uname -a`, точные значения `sysctl`, дату, статус сети (отключена на время опытов), наличие снимка. Исходные данные автоматически сохраняет `scripts/collect_environment.sh`.

Для любого теста документируем: **гипотеза → команда/код → ожидаемое поведение → наблюдение → скриншот → вывод**. Без заполнения реальными логами нельзя приписывать конкретные результаты Kali.

## 4.2. Э-1: System V и POSIX обмен

**Гипотеза:** процесс-отправитель передаст сообщение дочернему процессу, после завершения временная очередь будет удалена.

**Выполнение:** `./bin/sysv_demo`, `./bin/posix_demo` и соответствующие `strace` из README.

**Метрика:** факт получения, PID отправителя/получателя, число байт, приоритет POSIX; проверка `CLEANUP=OK`.

**Скриншот:** 05–07. **Вывод (заполняется):** `____________`.

## 4.3. Э-2: System V MSGMNB и MSGMAX

**Гипотеза:** при размере payload 512 байт System V очередь с `msg_qbytes` 4096 или 2048 вместит ограниченное число сообщений, после чего неблокирующая отправка вернёт `EAGAIN`. При отправке сообщения длиннее `kernel.msgmax` — `EINVAL`.

**Выполнение:** `./bin/sysv_limits 4096` и `./bin/sysv_limits 2048`.

**Метрики:** `queue_bytes_limit`, `payload`, `sent`, `used_bytes`, `errno_full`, `SYSV_OVERSIZE`. Скриншот 08. Допуск: если локальный исходный `msg_qbytes` меньше запрошенного, программа ограничит итоговое значение; число сообщений может отличаться. Изменение лимита затрагивает **только созданную очередь**.

## 4.4. Э-3: POSIX mq_maxmsg/mq_msgsize

**Гипотеза:** при `mq_maxmsg` 4 и 2 очередь вместит соответствующее число сообщений, превышение количества вызовет `EAGAIN`, размера — `EMSGSIZE`.

**Выполнение:** `./bin/posix_limits 4`, `./bin/posix_limits 2`.

**Метрики:** `maxmsg`, `msgsize`, `curmsgs`, `errno_full`, `POSIX_OVERSIZE`. Скриншот 09. При необычно низких `fs.mqueue.msg_max` или `msgsize_max` программа автоматически уменьшает запрос.

## 4.5. Э-4: контроль доступа

**Гипотеза:** учётная запись `nobody` не сможет запросить чтение System V объекта, принадлежащего другому пользователю и созданного с правами `0600`.

**Выполнение:** `./scripts/permissions_test.sh`.

**Метрика:** `DENIED errno=13 (EACCES) EXPECTED`. Скриншот 13. Проверка не доказывает отсутствие иных ошибок безопасности.

## 4.6. Э-5: изоляция namespace

**Гипотеза:** очередь System V с ключом, существующая в исходном IPC namespace, не будет найдена в созданном через `unshare --ipc` пространстве.

**Выполнение:** `sudo ./scripts/namespace_test.sh`.

**Метрика:** разные inode IPC namespace и `NAMESPACE HIDDEN ... ENOENT`. Скриншот 14. Если `unshare` запрещён — записать как «не выполнено по ограничениям стенда».

## 4.7. Э-6: лимиты числа очередей и sysctl

**Гипотеза:** изменение параметров `kernel.msgmnb` и `kernel.msgmni` только внутри нового namespace приводит к меньшей вместимости очереди и `ENOSPC` при попытке создать лишние объекты, не изменяя исходные значения системных лимитов.

**Выполнение:** `sudo ./scripts/sysctl_namespace_test.sh`.

**Метрики:** внутренние `msgmnb=2048`, `msgmni=4`; `QUEUE_COUNT requested=6 created=4 stop_errno=28 (ENOSPC)` — ожидаемое при свободном namespace, может отличаться, если там есть другие очереди. Скриншот 15. Важна проверка значений `sysctl` вне нового namespace **после** завершения.

## 4.8. Э-7: ограниченная нагрузка и состояние памяти

**Гипотеза:** при 8 очередях с объёмом 2048 байт одна очередь заполнится до лимита, а системные метрики состояния IPC покажут временные объекты; после завершения объекты исчезнут.

**Выполнение:** `./scripts/run_experiments.sh`, в составе которого `resource_probe 8 2048 5`.

**Метрики:** `queues_created`, `messages`, `payload_bytes`, `ipcs -u`, `/proc/sysvipc/msg`, `MemAvailable`, `Slab`, `SReclaimable`, `SUnreclaim` в три временных точки. 8×2048 = **16 384 байта полезных данных** (плюс служебные накладные расходы ядра). Нагрузку нельзя называть полноценным DoS; это безопасная модель исчерпания квоты. Динамика `Slab` в такой маленькой нагрузке может быть неразличима на фоне системы — это корректное наблюдение, не ошибка исследования.

**Скриншоты:** 10–12, 16. Зафиксировать не только положительный, но и отрицательный/неопределённый результат измерений.

## 4.10. Корректные научные выводы

`EAGAIN`, `EINVAL`, `EMSGSIZE`, `ENOSPC`, `EACCES`, `ENOENT` при описанных условиях — ожидаемые ответы API. Они не устанавливают конкретный идентификатор CVE, но подтверждают работу защитных границ на изучаемом стенде. CVE анализируются отдельно на основе записей и исправлений ядра.
