# Глава 5. Практические рекомендации по защите IPC очередей

## 5.1. Уровень ядра и системы

1. **Поддерживать ядро и пакеты актуальными.** При оценке CVE изучать пакеты Kali/Debian и backport-фиксы, не только upstream номер версии (обоснование: CVE-2015-7613, CVE-2017-11176, CVE-2021-47069).
2. **Ограничивать размеры и число очередей по реальной задаче приложения.** Для System V это `msgmax`, `msgmnb`, `msgmni`, для POSIX — `fs.mqueue.*`, `mq_attr` и `RLIMIT_MSGQUEUE`. Значение 2048 байт использовано как **учебное**, оно не подходит универсально всем продуктивным сервисам.
3. **Изолировать IPC workloads в отдельных IPC namespaces**, если архитектура приложения и окружение позволяют. При этом не путать IPC namespace с полной изоляцией ОС.
4. **Ограничивать полномочия:** не выдавать `CAP_IPC_OWNER` и `CAP_SYS_RESOURCE` приложению без необходимости. Не запускать всё приложение от root ради доступа к одной очереди.
5. **Рассматривать hardening ядра как дополнительный слой**, а не как исправление CVE. В частности, KASLR, проверки целостности, настройки slab-аллокатора и прочие механизмы актуальны только при наличии поддержки в конкретной сборке.

**Пример безопасной оценки без изменения host sysctl:**

```bash
sysctl kernel.msgmax kernel.msgmnb kernel.msgmni
sysctl fs.mqueue.queues_max fs.mqueue.msg_max fs.mqueue.msgsize_max
./bin/sysv_limits 2048
./bin/posix_limits 2
```

Постоянные значения системных лимитов следует выбирать по профилю нагрузки, данным мониторинга и требованиям сервиса; публиковать их как «волшебную защиту» некорректно.

## 5.2. Мониторинг и аудит

- Наблюдать изменение количества очередей и суммарного объёма: `ipcs -u`, `ipcs -q`, `/proc/sysvipc/msg`.
- Отслеживать необычно частые отказы `EAGAIN`, `ENOSPC` в логах **своего приложения**, чтобы не путать пиковую нагрузку с дефектом.
- При необходимости на стенде дополнить трассировкой `strace`, auditd / eBPF с учётом затрат на производительность и приватности событий.
- Применять AppArmor/SELinux в соответствии с профилем конкретного приложения; не считать, что политика автоматически перекрывает все варианты System V или POSIX IPC без проверки правил.

## 5.3. Безопасная разработка

- Использовать минимальные права (`0600` для личной очереди), применять `umask` и проверять итоговый режим объекта.
- Всегда проверять коды возврата `msgget`, `msgsnd`, `msgrcv`, `msgctl`, `mq_open`, `mq_send`, `mq_receive`, `mq_unlink`; различать `EINTR`, `EAGAIN`, `EINVAL`, `EMSGSIZE`, `EACCES`.
- Избегать блокировки без тайм-аутов в критических сервисах; предусмотреть bounded-retry, очередь ограниченной длины, backpressure.
- Освобождать объект на всех путях выполнения и при корректном завершении: `IPC_RMID` для System V и `mq_unlink` для POSIX. При аварии очистка может не выполниться — у сервиса должна быть стратегия восстановления.
- Не формировать фиксированные глобальные ключи без необходимости; если требуется именованный объект, предотвращать неожиданное повторное использование (`IPC_EXCL`, `O_EXCL`), где это применимо.
- В отдельной ВМ воспроизводить поведение разных лимитов перед внесением изменений в работающую инфраструктуру.

## 5.4. Контрольный список

- [ ] Ядро обновляется, проверены патчи для применимых CVE.
- [ ] Объекты создаются с минимальными правами.
- [ ] `msgmax`, `msgmnb`, `msgmni`, `fs.mqueue.*` оценены по реальной нагрузке.
- [ ] Учтены `RLIMIT_MSGQUEUE` и пользовательские квоты.
- [ ] Объекты удаляются после завершения работы.
- [ ] Неблокирующие операции/тайм-ауты обрабатывают ожидаемые ошибки.
- [ ] Нагрузка изолирована, если это необходимо и доступно.
- [ ] Мониторинг проверяет необычное увеличение числа очередей.
- [ ] Приложения не получают лишние capabilities.
- [ ] Нет экспериментов на производственных системах без согласования.

## 5.5. Привязка рекомендаций к результатам

| Практический результат | Рекомендация |
| --- | --- |
| `EAGAIN` при заполнении | Ввести политику backpressure, подбирать `msg_qbytes`, `mq_maxmsg` |
| `EINVAL` / `EMSGSIZE` | Проверять длины и корректность сериализации сообщений |
| `EACCES` | Выбирать строгие права IPC-объекта |
| `ENOENT` в IPC namespace | Изолировать независимые workloads, не полагаясь только на DAC |
| `ENOSPC` при низком `msgmni` | Ограничивать число очередей и удалять неиспользуемые |
| CVE UAF/race | Устанавливать патчи ядра, применять hardening, не подменять патчи sysctl-лимитами |

## 5.6. Вывод

Защита подсистемы IPC многоуровневая: исправленное ядро, ограничение ресурсов, минимальные привилегии, правильное управление жизненным циклом очередей и наблюдаемость. Для каждой настройки нужен измеримый эффект и понимание компромисса с доступностью.
