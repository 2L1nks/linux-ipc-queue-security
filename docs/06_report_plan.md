# План итогового отчёта по курсовой

Отчёт составляется **после** проведения экспериментов в Kali. Этот документ — рабочий шаблон структуры, а не выдуманный набор результатов.

## Введение (1–2 страницы)

- Актуальность: высокая значимость IPC для системных сервисов и роль изоляции/ограничений.
- Объект: подсистема IPC ядра Linux.
- Предмет: безопасность System V/POSIX очередей сообщений.
- Цель и шесть задач — формулировки из утверждённого плана курсовой.
- Методы: первичные источники и код ядра, анализ CVE, эксперименты в изолированной ВМ, сравнение.
- Этические ограничения: без exploit chain и тестирования чужих систем.

## Глава 1. Теоретические основы (3–5 страниц)

Рассмотреть IPC, сравнение System V и POSIX, API, структуры ядра. Добавить **рисунок 1** (архитектура IPC) и **рисунок 2** (путь сообщения) из `docs/01_theory.md`. Проверить соответствие схем изучаемой версии ядра.

## Глава 2. Модель безопасности (3–4 страницы)

Таблица DAC/capabilities/namespaces/sysctl, карта точек риска. Снимки IPC-лимитов стенда (скриншот 03). Обсудить пределы каждой меры.

## Глава 3. Обзор CVE (3–5 страниц)

Вставить сводную таблицу из `docs/03_cve_review.md` / `docs/CVE_TABLE.csv`. Для каждой CVE источник, сценарий ошибки, класс, последствия, upstream-фикс и осторожная оценка актуальности для вашей Kali (проверка backport!). Отдельно пояснить, что `msg_msg` как вспомогательный объект в цепочке другой CVE не означает дефект в очередях.

## Глава 4. Практическая часть (6–10 страниц)

1. Конфигурация стенда: снимки 02–04, версия гипервизора/ядра, параметры из `environment.txt`.
2. Э-1: обмен сообщениями, снимки 05–07.
3. Э-2 и Э-3: лимиты, снимки 08–09, количественные таблицы.
4. Э-4: DAC, снимок 13.
5. Э-5: namespace, снимок 14 или зафиксированное ограничение стенда.
6. Э-6: `msgmnb/msgmni` в namespace, снимок 15 либо зафиксированное ограничение.
7. Э-7: ограниченная нагрузка, снимки 10–12 и 16, SVG-график и временные точки состояния IPC.
8. Интерпретация: почему успешные границы безопасности не доказывают CVE, ограничения методики и повторяемость.

Для каждого опыта дать гипотезу, команду/параметры, наблюдение и вывод; код полностью перенести в приложение или дать ссылку на коммит GitHub.

## Глава 5. Рекомендации (2–3 страницы)

Опираясь на конкретные эксперименты, сформулировать ограничения ресурсов, принципы очистки объектов, namespaces, минимальные права, обработку ошибок, необходимость патчей ядра и мониторинга. Включить контрольный список из `docs/05_recommendations.md`.

## Заключение (1–2 страницы)

По каждой задаче коротко указать достигнутый результат. Отметить особенности современных ядер, ограниченность тестирования на одном релизе, возможные будущие направления (например, безопасное фаззинг-тестирование в отдельной ВМ). Не утверждать, что обнаружена эксплуатируемая уязвимость, если этого не показал эксперимент.

## Приложения

- Листинги `src/*.c`, `Makefile`, `scripts/*.sh`.
- Логи, скриншоты и график только со **своей** Kali.
- Ссылка на приватный/публичный GitHub репозиторий и hash итогового коммита.
- Список литературы по правилам своего вуза / ГОСТ; URL и даты обращения из `docs/SOURCES.md`.

## Материалы, которые понадобятся для оформления готового отчёта

После выполнения проекта подготовьте: ZIP выбранных логов `results/sanitized/`, 16 скриншотов (или пометки об отказе экспериментов), фактический `uname -a`, модель гипервизора/память/CPU, ссылку на GitHub, вузовский шаблон или требования оформления, точные ФИО/группа/руководитель **только когда будете готовы включать их в отчёт**. Отчёт не создан на этом этапе — сперва нужны данные Kali.

## Если GitHub-репозиторий уже создан

Вместо повторного `gh repo create` можно подключить существующий пустой репозиторий:

```bash
git remote add origin https://github.com/YOUR_USERNAME/linux-ipc-queue-security.git
git push -u origin main
```

Если `origin` уже есть — не добавляйте его повторно. Проверка: `git remote -v`; при необходимости меняйте URL через `git remote set-url origin ...`.
